# イシューに着手する準備をする

出すのは **ブランチ 1 本と計画 1 枚**だけ。コードも設計書も書き換えない。

順番に意味がある。**ブランチより先に設計書を読まない**のは、どの単位の話か決まる前に読むと関係ない節まで読むから。**計画より先に環境を確かめる**のは、計画が通ってから環境で止まると人を何度も待たせるから。**計画を書き切る前に決めごとを聞く**のは、黙って決めた分だけ、あとで設計書と実物がずれるから。

**plan モードに入るのは手順 5 から。**手順 1 のブランチ作成と手順 3 の環境確認（`sail up`・`key:generate`・`migrate`）は書き込みなので、plan モードの中ではできない。先に済ませておく。

## 0. 対象のイシューを決める

- 番号が引数にあればそれを使う。無ければ `gh issue list` で開いているものを出して、どれかを聞く。
- `gh issue view <N>` で **概要 / 完成の条件 / 決めごと / 変えないもの**を読む。
- `docs/design/acceptance.md` の **1 章の対応表**で、そのイシューが 7 つの実装単位のどれかを決める。イシューの F 番号ではなく**単位の番号**で引く（本書は F 番号を 7 単位に束ねている）。特定できないときは聞く。
- 単位が決まったら **AC-<単位>-◯**（2 章）と **T-<単位>-◯**（3 章）を引く。前者が「できたと言える条件」、後者が「テストで確かめる観点」。この 2 つが計画の背骨になる。

**例**: イシュー #1「社員が自分でアカウントを作ってログインできるようにする」→ 1 章の表で**単位1（認証）**→ AC-1-1〜AC-1-4 と T-1-01〜T-1-20。

## 1. ブランチを用意する

- 先に `git status` で作業ツリーがきれいか見る。汚れていたら、捨ててよいか聞く。
- `main` に切り替え、`origin` から pull する。
- 名前は `CLAUDE.md` の「ブランチとプルリクエスト」に従う。
- **同じ名前のブランチが既にあったら、切り直す前に `git log --oneline main..<ブランチ>` を見る。**0 件なら中身が無いので切り直してよい。1 件でもあれば、人の作業を捨てることになるので必ず聞く。

## 2. 設計書を必要な節だけ読む

`docs/design/` は合計 3,000 行を超える。全文は読まない。まず `grep -n '^#\{1,4\} ' docs/design/<file>.md` で見出しを出し、**その単位に関わる節だけ**開く。

| 読む順 | ファイル | そこから取るもの |
|:--|:--|:--|
| 1 | `README.md` | どのファイルに何があるかの表 |
| 2 | `acceptance.md` | 1 章の対応表 → 2 章の AC → 3 章の T観点 |
| 3 | `screens.md` | 画面項目・入力チェック・**文言**（文言はここが正本） |
| 4 | `permissions-api.md` | URL・ルート名・ミドルウェア・404 と 403 の線引き |
| 5 | `behavior.md` | 例外方針・JavaScript の範囲・初期状態から変えるところ |
| 6 | `data.md` | 列・型・制約・CRUD |
| 7 | `mockup/` | 該当 HTML と `design-guide.md`（クラス名と色） |

- `CLAUDE.md` の「守ってほしい書き方」から、**その単位に当たる行**を拾う。素直に書くと破れる決めが並んでいる。
- **`docs/spec.md` と `mockup/` は読むだけで変えない。`.env` は中身を読まない**（`.env.example` を見る）。

## 3. 動く環境か確かめる（計画を書く前に）

ここを飛ばすと、計画が通ったあとに止まる。実際に止まった 4 つを順に見る。

| 見るもの | 確かめ方 | 止まったときどうするか |
|:--|:--|:--|
| 依存 | `ls vendor/bin/sail` | 無ければ `composer install`。`vendor/` が無いと Sail 自体が無い（卵と鶏）ので、Composer はコンテナで回す |
| `.env` | `ls -a \| grep -i env` | **無くても自分では作れない**（`.claude/settings.json` の `deny` に `Edit(.env)`）。`! cp .env.example .env` を人に打ってもらう |
| コンテナ | `docker ps` | 落ちていれば `sail up -d`。`APP_KEY` が未設定なら `sail artisan key:generate` |
| ポート | `docker ps --format '{{.Names}}\|{{.Ports}}'` | **80・3306 を別プロジェクトが使っていないか。**使っていたら、止めてよいかを必ず聞く（人の作業が動いているかもしれない） |
| DB とテスト | `sail artisan migrate` と `sail artisan test` | ここで初めてテストを 1 回通す。落ちていれば、その原因を計画に書く |

PHP の版やイメージの非推奨通知のように**判断が要るもの**は、勝手に変えずに計画へ上げるか、4 で聞く。

ここで直らないものは、計画の先頭に「0. 環境の立ち上げ」として**誰が何をやるか**まで書く。

## 4. 決めごとを洗い出して、人に聞く

計画を書き切る前に聞く。出てくるのはだいたいこの 3 つの型。

| 型 | 中身 | 聞き方 |
|:--|:--|:--|
| **食い違い** | `CLAUDE.md` と `docs/design/` が違うことを言っている | どちらを正にするか。寄せなかった側を直すことになるので、どのファイルがどう変わるかまで見せる |
| **根拠が無い選択** | 設計書にもモックアップにも元が無い（文言・画面の枚数・入れるライブラリ） | 選択肢を出す。推奨を先頭に置き、理由を 1 行で |
| **範囲** | 隣の単位とどこで切るか（この画面は今回作るのか） | 作るもの・作らないものを並べて見せる |

- `AskUserQuestion` を使い、**選んだ結果どのファイルがどうなるか**を preview に入れる。言葉だけだと選びにくい。
- **答えに依存しない調べものは先に済ませておく。**聞いている間に止まらない。
- 聞いた答えは、そのまま計画の「先に決めたこと」の表になる。

## 5. 計画を立てるか、ひと言で済ませるかを分ける

**全部に計画が要るわけではない。**計画は相手に読む時間を使わせるので、読む価値があるときだけ書く。

| 見るところ | 計画を立てる（plan モードに入る） | ひと言伝えて着手する |
|:--|:--|:--|
| AC 番号 | **付く**（`acceptance.md` の実装単位にあたる） | 付かない |
| 触るもの | アプリのコード・マイグレーション・設計書 | `.claude/` の手入れ、文言や表記の揃え、1 ファイルの数行 |
| 決めごと | 人に聞くことが 1 つでもある | 「やるか・やらないか」だけ |
| コミット | 何本かに分かれる | 1 本で足りる |
| この案件での例 | 単位1 認証（AC-1-1〜AC-1-4・41 ファイル） | 405 のエラー画面を 1 枚足す／`testing.md` のコマンド表記を揃える |

**計画を立てる道**

1. `EnterPlanMode` で plan モードに入る。
2. 下の型で計画を書く。plan モードでは計画ファイル以外を書き換えられないので、調べものは読み取りだけで進める。
3. 残っている決めごとは、計画を書き切る前に `AskUserQuestion` で聞く（手順 4）。
4. `ExitPlanMode` で承認をもらう。**承認を求めるのはこのツールだけ**で、「この計画でいいですか」と本文で聞かない。

**ひと言で済ます道**

- **plan モードには入らない。**計画ファイルも作らない。
- 代わりに、**何をするかを数行**で伝える: 触るファイル、変える中身、確かめ方。
- そのうえで承認をもらってから着手する。**伝えるのと同じ返信で手を動かさない。**
- 例: 「`.claude/rules/testing.md` の `sail test --filter` を `sail artisan test --filter` に直します（1 行）。ほかのファイルは触りません。進めてよいですか。」

**迷ったとき**は、やることを数行で出して「このまま進めるか、計画にするか」を相手に選んでもらう。1 往復で済むし、計画が要るかどうかを一番よく知っているのは相手。

## 6. 計画を 1 枚書く（計画を立てる道のとき）

計画ファイルに、この見出しの並びで書く。

```
Context          なぜこの作業をするのか、何を作るのか、いまどこから始めるのか
先に決めたこと    4 で聞いた答えの表（決めたこと / その影響）
0. 環境の立ち上げ  3 で直らなかったぶん。誰が何をやるか
作業の順番        触るファイル名つき。設計書の節番号で根拠を指す
設計書を直すところ あれば。コードより先に直すと書く
テスト            acceptance.md の T観点を番号で指す。確かめる内容は写さない
確かめ方          sail のコマンドと、ブラウザで見る AC
コミットと PR     `/pr` の型に従う（ブランチ名は CLAUDE.md）
```

書き方の決まり:

- **設計書の中身を写さない。節番号で指す**（`screens.md` 4-3 のとおり、など）。写すと同じことが 2 か所に増え、設計書を直したときに計画が古くなる。
- **作らないものと、その行き先の単位を必ず書く。**あとで「なぜ無いのか」を調べ直さずに済む。
- 判定できないことは「判定できない」と書く。確かめていないものを「満たす」と書かない。
- 範囲が変わったら、追記ではなく**その 1 枚を書き直す**。古い計画が残っていると、どれが生きている決めか分からなくなる。

## 7. 承認が出たら実装に入る

どちらの道でも、**承認が出てから**手を動かす。ここでこのスキルの役目は終わり。実装は `CLAUDE.md` の「実装の決まり」「守ってほしい書き方」「テスト」に従う。

承認のときに範囲が変わることがある（今回も 3 回変わった）。そのときは追記ではなく**計画の 1 枚を書き直す**。古い計画が残っていると、どれが生きている決めか分からなくなる。

## やらないこと

- **承認が出る前にコードを書かない。**計画を出す道でも、ひと言で済ます道でも、伝えるのと同じ返信で手を動かさない。
- **`docs/design/` を直さない。**直す必要が見つかったら、計画に「ここを直す」と書くところまで。
- イシューの本文を編集しない。
- テストを回すのは 3 の確認で 1 回だけ。赤を直しにいかない（それは実装の仕事）。
