# 機能のイシューを 1 件たてる

渡された受け入れ条件と決めごとを、既存イシューの書式に揃えて GitHub に 1 件たてる。実装はしない。

## 1. 書式を既存イシューに揃える

直近のイシューを見て、見出しの並びと文体を確かめる。**まだ 1 件も無いときは、下の書式をそのまま使う。**

```bash
gh issue list --state all --limit 5
gh issue view <直近の番号>
```

今の書式は次のとおり（イシューに ラベル は付けていない。`gh label list` は見なくてよい）。

1. `## 概要` — 1〜2 文。何ができるようになるか。
2. `## 完成の条件` — `- [ ]` のチェックリスト。
3. `## 決めごと` — 表（`決めごと | 中身`）。渡されたときだけ入れる。
4. `## 変えないもの` — 箇条書き。

## 2. 中身を組み立てる

- 渡された要望を読み、いまのコード（`routes/`・`app/`）と `docs/design/` の設計書一式を見て、決めないといけないことが残っていないかを確かめる。
    - その機能の受け入れ条件が `docs/design/acceptance.md`（2 章の AC 番号）にすでにあるときは、**そこにある文言をそのまま写す**（言い換えない。設計書とイシューで文言を揃えるため）。
- **受け入れ条件は一字一句そのまま**「完成の条件」に入れる。言い換えない、足さない、減らさない。
- 決めごとの表は渡された内容をそのまま入れる。**「自分とAIで決めて構いません」と任された項目だけ**、こちらで決めて表に書く。
    - 決め方に制約があれば守る（例: 画面に出る文言は `docs/design/screens.md` の決めから外れない名前）。
- 「変えないもの」は、`docs/design/features.md` の「今回作らないもの」と、すでに作り終えた実装単位（`docs/design/acceptance.md` 1 章の 7 単位）から、機能が触る範囲を選んで書く。**渡されていない項目を足したときは、報告でそう伝える。**
- タイトルは「〇〇を〜する」の形（例: `チャンネルを作れるようにする`）。

## 3. たてる

タイトルと本文を確かめてから、1 件だけ作る。本文はヒアドキュメントで渡す。

```bash
gh issue create --title "<タイトル>" --body "$(cat <<'EOF'
## 概要
...
EOF
)"
```

- 同じ内容のイシューが既に開いていないかを `gh issue list` で見て、あれば作らずに知らせる。
- 作り直しや編集（`gh issue edit`）は、頼まれたときだけ。

## 4. 報告する

- イシューの URL。
- 受け入れ条件はそのまま入れたこと。
- こちらで決めた項目と、足した「変えないもの」。
- ラベルは付けていないこと、実装は始めていないこと。
