# PR を設計書と突き合わせて読む

PR の差分を、設計書（`docs/design/*.md`）→ 触らないはずの場所 → 中身 の順に読み、観点ごとの表で報告する。コードは直さない。直すかどうかを決めるのは人なので、この Skill の仕事は「どこを見れば判断できるか」を渡すところまで。

順番に意味がある。設計書との突き合わせを先にやると、「書いていないものが増えていないか」という全体の枠が決まり、そのあとの細かい読みが枠の内か外かで迷わない。中身の読みを最後にするのは、枠の外の変更ほど人が見るべき度合いが高く、そこに時間を割きたいから。

## 0. 対象を決める

- PR 番号が引数にあればそれを使う。ない、または `<番号>` のような未置換の文字が残っているときは `gh pr list --state merged` で一覧を出す。候補が 1 件ならそれを対象にして、どの PR を読むかを報告に書く。複数あるときは聞く。
- 次を取る。
    ```bash
    gh pr view N --json title,body,baseRefName,headRefName,mergeCommit,additions,deletions,changedFiles
    gh pr diff N --name-only
    gh pr diff N > <scratchpad>/prN.diff      # 1000 行を超えることがあるので一度ファイルに落とす
    ```
- **行番号はマージ時点のもので出す。** main はその後も動くので、現在のファイルの行番号は PR の差分とずれる。`git show <mergeCommit.oid>:<path> | grep -n ...` で確定させ、報告には「行番号はマージ時点」と書く。未マージなら head ブランチ。
- 設計書は常に `docs/design/` にある。PR 本文の `Closes #N` と `単位◯` から、`acceptance.md` 1 章の表で対象の単位と AC 番号を決める。単位が特定できないときは聞く。
- 設計書が PR 時点から変わっていないかを `git diff <mergeCommit.oid> HEAD -- docs/design/` で確かめ、変わっていれば報告に書く。

## 1. 設計書と突き合わせる

設計書の次の節を、差分の実際の変更と 1 つずつ照らす。

- 受け入れ条件は `acceptance.md`、画面は `screens.md`、テーブルは `data.md`、権限と API は `permissions-api.md`: 設計書どおりに実装されているか（列・ルート・文言）。
- `features.md` の「今回作らないもの」と、すでに作り終えた単位: 差分がそこに触っていないか。
- **設計書に書いていないものが増えていないか。** `--name-only` の一覧から、設計書の画面・テーブル・テスト観点のどれにも対応しないファイルを洗い出す。`composer.json` / `composer.lock`（依存の追加）、`CLAUDE.md`、設定ファイル、他機能のテストは特に目を留める。差分に入っていないことも「OK（差分になし）」として報告に残す。
    - 設計書に書いていないことが実装されていたら、コードと設計書のどちらが正かを人に聞き返す。勝手にどちらかへ寄せない。
- **PR 本文の主張を差分で裏取りする。** 「既存メソッドは無変更」「テスト N 件通過」のような一文は、差分と食い違っていることがある。食い違いは要確認。テスト結果は自分で回していなければ「判定できない（実行していない）」とする。

## 2. 触らないはずの場所を見る

触らないはずのファイルを具体的に挙げて読む。全機能が共有するのは `routes/web.php`・`routes/api.php`・`app/Policies/`・`database/migrations/`・`config/` の 5 つ。機能ごとに `docs/design/` の該当節からも選び直す。

- **消えた行（`-`）から先に読む。** 追加行は新機能のものだが、消えた行は今ある動きを壊す可能性がある。消えた行が何で、同じ中身で戻っているか（インデントだけの変更か）、意味が変わっていないか（`@csrf`・`@method`・`@can`・`with()` が残っているか）を確かめる。
- 消えた行が 0 の追加だけの変更も、読んだ結果として「OK」と残す。ルートなら、新しい `/{id}` 系が既存の固定パス（`/channels/create` など）を飲み込まない並びかを `permissions-api.md` のルーティング一覧と見比べる。
- 変更されていない（差分にない）のに「触らない」と指定されたファイルは、「OK（差分になし）」とする。
- 見た目の変化（余白・表示条件）はテストが HTML 文字列しか見ていないと確認できない。画面を見ていなければ「判定できない」と書き、何が足りないか（ブラウザで 2 ユーザーを切り替える、など）を添える。

## 3. 中身を読む

`CLAUDE.md` の「実装の決まり」と `docs/design/` をチェックリストの出どころにして、次の観点を読む。

- **N+1**: ビューが引く関連が、コントローラーの `with()` / `load()` に入っているか（差分で確かめる）。`@can` が内部でクエリを打たないかも見る。
- **認可の置き場所**: コントローラーの `$this->authorize(...)` とビューの `@can` の両方があるか。判定が `permissions-api.md` 1-3 の権限マトリクスどおりか。404 と 403 の順番（先に「チャンネルを見られるか」→ 次に「本人か・作成者か」）が 1-5 の線引きどおりか。
- **マスアサインメント**: `$fillable` の中身と、`create` / `update` に渡している配列の出どころ（`$request->all()` でなく `validate()` の戻り値か。`user_id` をサーバー側で決めているか）。
- **XSS**: `{!! !!}` や `style=` / `href=` / `<script>` に入る値がエスケープ・定数由来か。
- **CSRF**: 送信フォームと `@method` 付きの削除フォームに `@csrf` があるか。ルートが `web` グループか。
- **入力チェック**: 必須・上限・日本語メッセージ（`validate()` の第 2 引数）が `screens.md` の入力チェックとメッセージ一覧どおりか。`config/app.php` の `locale` が `en` なので、メッセージを指定していない項目は英語になる。文字数を前後の空白と改行を取り除いたあとで数えているか（`screens.md`）、`old()` で入力が残るかも見る。
- **書き方の揃い**: 周りのコードと命名・コメント量・テストの書き方が揃っているか。コピーされた重複（同じ検証コードが 2 か所、同じ配列が 2 つのビュー）は、値が一致しているかまで確かめて報告する。
- **モデルを持たない機能の名前**: 認証・検索のようにモデルを持たない機能は、`data.md` に照らす先がない。**Laravel とパッケージの標準の名前（`AuthenticatedSessionController`・`RegisteredUserController` など）に揃っていれば OK とする。**
  設計書のどの表にも出てこないことを理由に「要確認」にしない。標準から外れた自前の名前を付けているときだけ、どこから来た名前かを報告する。

読み終えて確信が持てない観点は、無理に OK にしない。「何が足りなくて判定できないか」を必ず書く（実機で動かしていない、他のファイルを見ていない、など）。

## 4. このアプリの決めごとに沿っているか

`docs/design/` で決めた、**コードを読まないと分からない決めごと**を見る。どれも直さず、「人が読むべき場所」として報告する。

- **判定の順番**: `MessagePolicy` の `update`・`delete`・`reply` が、メッセージ自体（本人か・削除済みでないか）より先に `ChannelPolicy@view` を通しているか。逆だと、プライベートチャンネルから外された人が自分の過去のメッセージを直せてしまい、403 でそのチャンネルの存在も漏れる（`permissions-api.md` 1-5・1-6）。
- **削除済みの本文の 3 つの出口**: 画面（`withTrashed()` で引く・出し分けは Blade 部品 1 か所に閉じる）／検索（`withTrashed()` を書かない）／公開 API（返す列を許可リストにして `body`・`deleted_at` を出さない）。**経路が別なので、1 つ塞がっていても残りは塞がらない。**差分では 3 経路を別々に確かめる（`questions.md` 決定1 / `behavior.md` 3-6）。
- **返信件数の数え方**: 画面は削除済みの親・子を含めて数え（`withCount` の既定では落ちる）、公開 API は削除済みの返信を含めない。書き忘れると「返信3件」が静かに「2件」に減る（`behavior.md` 1-4）。
- **「見られるチャンネル」が 1 か所を通っているか**: サイドバー・チャンネル一覧・検索・チャンネルの取得が、すべて `Channel` の `visibleTo` スコープ経由か。差分に自前の `where` が増えていたら、それが抜け道になる（`permissions-api.md` 1-6）。
- **制約にできず約束で守る決まり**: 「返信は 1 段まで」「返信の `channel_id` は親と同じ」「チャンネル名の重複はその人が見られる範囲だけで見る」。`channels.name` に一意制約が増えていたら、見えないチャンネルの存在が漏れる（`data.md` 4-3）。
- **まとめて書くところ**: チャンネル作成（`channels` ＋ 作成者の `channel_user`）・チャンネル削除・初期データが 1 つのトランザクションに入っているか。チャンネル削除は物理削除で、`$channel->delete()` では中のメッセージが消えない（`behavior.md` 3-5 / `data.md` 2-5）。
- **入力の前処理と画面の文言**: 前後の空白と改行を取り除いてから空を見て、上限もその後の文字数で数え、保存もその値か。文言が `screens.md` 4・5 の形（エラー文は句点なし 1 文、打った内容は残す、件数は「◯件」）か。
- **仮のまま進めた決めと申し送り**: 差分が `data.md` 4-4・`behavior.md` 5・`screens.md` 6 の未確定事項や、各設計書末尾の「申し送り」に触っているとき。回答が来たら直す場所なので、触ったことを報告に残す。

## 報告の形

観点ごとに 1 行、表にする。列はこの順。

| 観点 | 判定 | 場所 | 気づいたこと |
| ---- | ---- | ---- | ------------ |

- 判定は **要確認 / OK / 対象外** の 3 つ。判定できないときは判定欄に「判定できない」と書き、気づいたことに足りないものを書く。
- **「対象外」は、その観点が今回の差分に無いときだけ使う。**物差しが見つからないことを「対象外」で済ませない。
  照らす先が分からないときは「判定できない」にして、**何に照らせば判定できるのかが分からない**と正直に書く（例: 「この名前の正解がどの設計書にあるか分からない」）。黙って OK にするのと同じくらい、黙って対象外にするのも見落としになる。
- 場所は `ファイル名:行番号`（マージ時点）。差分に現れないものは「(差分になし)」。
- 気づいたことは事実と根拠を 1 文で。「こうすべき」の提案より、「設計書のこの行と食い違う」「ここが消えた」のように、人が確かめられる形で書く。
- 表は「1. 設計書との突き合わせ」「2. 触らないはずの場所」「3. 中身」「4. 決めごと」の 4 つに分ける。冒頭に対象の PR（番号・タイトル・マージ commit）と、行番号がマージ時点であること、設計書をどの版で見たかを 1〜2 行で書く。
- 最後に **「人が自分の目で読むべき場所」を 3 つまで** 挙げる。選ぶ基準は、要確認のうち設計書の枠の外にあるもの、消えた行があるもの、判断が人にしかできないもの（意図した変更か、設計書と PR 本文のどちらを直すか）。3 つに収まらなければ優先度で絞る。

## やらないこと

- コードや設計書を直さない。直す提案が必要なら、報告のあとで人が決めてから。
- テストを回さない（頼まれたときだけ）。PR 本文のテスト結果は「本文の記載」として扱う。
- 整形の揺れとテストの合否は報告に入れない。編集のたびにフックが全テストを回すので、人が読む量を増やさない。
