# 受け入れ条件とテスト観点

- 対象: チームチャットアプリ
- 典拠: `docs/spec.md`、`mockup/`（画面見本10枚・`design-guide.md`）、`docs/design/features.md`・`questions.md`・`screens.md`・`data.md`・`permissions-api.md`・`behavior.md`
- この文書は「**できたと言えるのは何が起きたときか**」だけを書きます。画面の中身は `screens.md`、データの持ち方は `data.md`、URLと権限は `permissions-api.md`、処理の流れと例外方針は `behavior.md` に分けます

---

## この文書の中の線引き

**受け入れ条件とテスト観点は、役割が違います。**同じことを両方に書きません。

| | 受け入れ条件（2章） | テスト観点（3章） |
|:--|:--|:--|
| 誰が使うか | **人**。実装が終わったあと、ブラウザで上から順に手で試します | **AIとテストコード**。網羅はこちらの仕事です |
| 量 | **1つの実装単位につき2〜4行**（`README.md` の決まり） | 観点の数だけ。ただし**観点まで**で、組み合わせは書き出しません |
| 書き方 | 「**〜すると、〜になる**」。ブラウザで操作すれば、合否がその場で決まる文にします | 「何を確かめるか」を1行で。手順と期待値はテストコード側に書きます |
| 落ちたとき | **実装が終わっていません** | 直す優先度はその場で判断します |

- 受け入れ条件を増やすと、人が確かめきれなくなります。**足したくなったら、テスト観点のほうに置きます**
- テスト観点には、ブラウザでは確かめにくいもの（データベースの中身・HTTPのステータス・応答に含まれる列・405・429・500）も入れます。受け入れ条件からはそれらを外しました

## 0. 試す前の前提（F-23 初期データ投入）

F-23（初期データ投入）は、ほかの7単位と並ぶ機能ではなく、**受け入れ条件を上から試すための前提**です。受け入れ条件の番号は振らず、ここに置きます。

**`php artisan migrate:fresh --seed` を実行すると、次の状態になります**（仕様書 5-4 / `data.md` 5）。

| 入っているもの | 中身 |
|:--|:--|
| アカウント | 3つ（パスワードが分かっていて、どれでもログインできる） |
| チャンネル | 4つ。**公開3つ・プライベート1つ**。プライベートの1つには、3アカウントのうち**1人が入っていない** |
| メッセージ | 公開チャンネルに各10件前後（古い順に日付をまたいで並ぶ） |
| 返信が付いたメッセージ | 2件以上。うち1件は**返信3件以上** |
| 「編集済み」のメッセージ | 1件以上 |
| 「削除されました」のメッセージ | 1件以上。**そのうち1件には返信が付いている** |

- プライベートチャンネルに入っていないアカウントが1つあることが、AC-2-2・AC-6-3 と T-2-13・T-6-07 の前提です
- 「削除されました」に返信が付いていることが、AC-5-3・AC-5-4 と T-5-05・T-5-06 の前提です（`questions.md` 決定1 の出口1-b・1-c を、いつでも手で確かめられるようにするため）
- この前提が崩れていると、下の受け入れ条件は試せません。**最初にここを確かめます**

- 番号は `T-<単位の番号>-<連番>` です
- **観点までです。**手順・入力値の組み合わせ・期待値の細部はテストコード側に書きます（`README.md` の「網羅はテストコードの仕事」）
- 区分は **正常系**（決めたとおりに動くか）／**異常系**（弾くべきものを弾くか）／**境界値**（上限・0件・ちょうどの値・数え方）です
- 「元になった設計書」は、その観点が**どこから来たか**です。設計を直したら、ここを辿って観点も直します

### 3-8. 書き方の決め（決定1の3つの出口）

`questions.md` 決定1 から持ち込んだ決まりです。**守らないと、観点があっても漏れが見えません。**

| 決め | 内容 |
|:--|:--|
| **出口ごとに独立に落ちるように書く** | 出口1（T-4-13・T-5-05）・出口2（T-6-09・T-6-10）・出口3（T-7-05・T-7-06）を、1つのテストで兼ねません。兼ねると、どこが緩んだのか分からなくなります |
| **「出ていないこと」で書く** | 「跡地の文言が出ている」ではなく、**「元の本文の文字列が出ていない」**で書きます。前者だけだと、跡地と本文が両方出ていても通ってしまいます |
| **列は許可リストで確かめる** | 出口3（T-7-05）は「返す約束のない列が無いこと」で確かめます。あとから列が増えたときに黙って漏れないようにするためです |
| **判定の順番を観点にする** | T-3-09・T-4-16 は「404 であること」まで見ます。**403 が返っていたらチャンネルの存在が漏れている**ので、そこが合否です |
