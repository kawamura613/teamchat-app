### Q-38 自分に見えないプライベートチャンネルと名前がぶつかったとき ◎（2回目でお聞きします）

- **気づいた場所**: 1回目の回答どうしがぶつかります。回答3「同じ名前のチャンネルは作れないようにしてください」と、回答1「入っていないプライベートチャンネルは、そういう部屋があること自体が分からない状態にしたい」の2つです。
- **何が起きるか**: 高橋さんが、自分の入っていないプライベートチャンネル「採用プロジェクト」と同じ名前でチャンネルを作ろうとしたとき、取れる道は2つしかありません。
  - 「その名前はすでに使われています」と断る → 名前は守られますが、**見えないはずの部屋があることが漏れます**（回答1に反する）
  - そのまま作らせる → 存在は隠せますが、**同じ名前が並びます**（回答3に反する）
- **想定**: **回答1（存在を隠すこと）を優先する**想定です。名前の重複を禁じるのは、その人が見られるチャンネル（公開チャンネル全部＋自分がメンバーのプライベートチャンネル）の中だけにします。見えないプライベートチャンネルとは、名前がぶつかってもそのまま作れます。「どちらに書けばよいか分からない」という困りごとは、両方が見えている人にしか起きないためです。
- **2026-10-30 の追記（この想定が成り立たない向きが1つあります）**: 上の「両方が見えている人にしか起きない」は、**公開チャンネルを作る向きでは成り立ちません。**
  1. 佐藤さんがプライベートチャンネル「採用プロジェクト」を作ります（高橋さんは入っていません）
  2. 高橋さんが**公開**チャンネル「採用プロジェクト」を作ります（高橋さんには1つめが見えないので、上の想定どおり作れます）
  3. **佐藤さんのサイドバーに「採用プロジェクト」が2行並びます**（公開チャンネルは全員に見えるため）
  - つまり「両方が見えている人」が、**作ったあとから生まれます。**回答3（同じ名前は作れないように）が、作成時点ではなく作成後に破れる形です。逆向き（プライベートを作る側）では起きません。**公開チャンネルを作るときだけの話です**
- **質問**: 次の2つをお聞きします。
  1. この優先順位でよろしいですか。それとも、存在が多少漏れても名前の重複を完全に避けたいですか。
  2. **公開**チャンネルを作るときだけは、**見えないプライベートチャンネルとの重複も弾きますか。**弾くと「その名前の部屋がある」ことが1件だけ漏れますが、同じ名前が2行並ぶことは防げます。
- **状態**: 回答なし／**クライアントへ確認中**（新規。1回目ではお聞きしていません。→ 0-6）

### 決定1 削除したメッセージの本文の持ち方

**決めたこと**: **案1**。メッセージの行（レコード）は残したまま `deleted_at` を立て、**`body` はそのまま残す**。Laravel の `SoftDeletes` を素の状態で使う。

**改訂の経緯**: 2026-10-29 には案2a（`body` を NULL にして本文を消す）を技術側の推奨としていました。2026-10-30 に案を6つまで広げて比べ直し、**案1（本文を残す）に変更**しました。変更の理由は「採った理由」の3番です。覆した判断なので、前の推奨も「採らなかった案」に残します。

#### 前提（どの案でも動かないこと）

**行そのものは必ず残ります。**理由は3つあり、すでに確定しています。

- 跡地に投稿者名と日時を出す（仕様書 3-4）
- 返信がぶら下がる先が要る（回答6「削除されたメッセージにも返信を続けられる」）
- 返信件数の表示を消さない。削除済みの返信も件数に含める（`design-guide.md` 4・Q-23）

さらに、モックアップ `thread.html` は**削除されたメッセージのスレッドが開いた状態**を描いています（`screens.md` 3-5）。「削除済みの親を取得して表示する」経路は、仕様として必ず要ります。

#### 2つの論点

案が多く見えるのは、独立した2つの軸を掛け合わせているからです。先に軸を分けると、何を選んだのかがはっきりします。

**軸1: 削除後、本文のデータをどこに置くか**

| 置き方 | 誤削除から戻せるか | 通常の読み取り経路に本文があるか | 該当する案 |
|:--|:--|:--|:--|
| **通常の行に残す** | ◯ 戻せる | **ある** | **案1 ← 採用** |
| NULL にする | ✕ | ない | 案2a |
| 別の場所に移す（退避テーブル） | ◯ 戻せる | ない | 案6 |
| 行ごと消す（跡地は別テーブル） | ✕ | ない | 案4 |

**軸2: 「削除済み」の印をどこで持つか**

| 持ち方 | 除外を書き忘れたときに倒れる向き | 該当する案 |
|:--|:--|:--|
| **`deleted_at` ＋ `SoftDeletes` のグローバルスコープ** | 跡地が消える・スレッドが404 ＝ **目に見える不具合（安全側）** | **案1・案2a・案6 ← 採用** |
| 自前のフラグ（グローバルスコープに乗らない） | 本文が検索結果と公開APIに出る ＝ **漏洩（危険側）** | 案3 |
| 本文行の不在で構造的に持つ | 本文が取れない ＝ 安全側 | 案5 |

**軸1が「復元できるか」と「漏れたときの被害の大きさ」を決め、軸2が「漏らさない手当ての重さ」を決めます。**採ったのは **軸1＝通常の行に残す／軸2＝`deleted_at`（`SoftDeletes`）** の組み合わせです。

#### 採った理由

1. **既定で安全な側から始められる。**`SoftDeletes` のグローバルスコープが削除済みを既定で除外するので、検索と公開APIは**素の実装のまま漏れません**。「除外を足していく」のではなく「除外されている状態から始める」形になります
2. **書き忘れが安全側に倒れる。**跡地を出す側で `withTrashed()` を忘れると、跡地が消える・スレッドが404になるという**目に見える不具合**になります。漏洩には倒れません（この向きが逆になる案3は落としました）
3. **誤削除から戻せる。**20人・社内・開発者がデータベースを触れる前提なら、「昨日の分を戻してください」というご依頼に応えられます。案2a・案4・案5では構造的に不可能で、**一度捨てると取り返せない性質の利点**です
4. **部品が増えない。**Laravel の素の機能（`SoftDeletes`・`restore()`・ルートの `->withTrashed()`。Laravel 10 で利用可）にそのまま乗り、独自の書き分けが要りません。案5・案6はテーブルが1つ増えます
5. **あとから方針を変えられる。**案1 → 案2a（消す）・案6（退避）への移行はできます。逆はできません

書き方の決め:

- **出口1・2・3のテストは、それぞれ独立に落ちるように書きます。**1つのテストで3つを兼ねると、どこが緩んだのか分からなくなります
- 本文の検査は「跡地の文言が出ていること」ではなく、**「元の本文の文字列が出ていないこと」**で書きます。前者だけだと、跡地と本文が両方出ていても通ってしまいます
- 出口3は「含まれないこと」を**列の許可リスト**で確かめます。あとから列が増えたときに黙って漏れないようにするためです
- 初期データ（F-23）には「削除されました」のメッセージが含まれます（仕様書 5-4）。**そのうち1件は返信が付いた状態**にして、出口1-b・1-c がいつでも手で確かめられるようにします

#### 採らなかった案

| 案 | 中身 | 採らなかった理由 |
|:--|:--|:--|
| 案2a | 行は残し、`body` を NULL にする（**2026-10-29 まではこちらを推奨していました**） | 出口1が「塞ぎ忘れても出ない」側になる利点はあるが、**誤削除から戻せない**。一度捨てると取り返せない利点を失う対価が大きいと判断。クライアントが「データごと消えていてほしい」と答えた場合はここへ切り替えます |

### 決定10（仮） 検索の当て方

**決めたこと**: Q-26 の想定どおり、**入力された文字列をそのまま含むもの（部分一致）**を探す。スペース区切りのAND検索はしない。大文字小文字は区別しない。

| 項目 | 決めたこと |
|:--|:--|
| 当て方 | **部分一致**（`WHERE body LIKE '%キーワード%'`）。入力は**1つの語**として扱います。スペースが入っていても分けません |
| 大文字小文字 | **区別しません。**MySQL の照合順序（`utf8mb4_unicode_ci`）に任せます |
| 表記の揺れ | **揺れも吸収します**（2026-11-03 に実測して訂正。もとは「吸収しません」と書いていました）。`utf8mb4_unicode_ci` はひらがなとカタカナ・全角と半角・アクセントの違いを**同じ字として扱う**ので、「りりーす」で「リリース」の本文が当たり、`cafe` で `café` が当たります。照合順序を変えるマイグレーションは足さない（`data.md` 4-4）ので、**この挙動を仕様として受け入れます** |
| 強調の当て方 | 抜粋の強調位置は PHP 側で探すので、**DB と同じだけ畳んでから位置を取ります**（ひらがな→カタカナ・全角英数→半角・小文字化。いずれも文字数が変わらない範囲）。**半角カナとアクセント付きの字は文字数が変わるため畳めません。**この 2 つで当たったときは、抜粋を**先頭から・強調なし**で出します（`screens.md` 3-5 / `acceptance.md` T-6-11） |
| 記号の扱い | キーワードに `%`・`_`・`\` が入っていたら**エスケープして文字として扱います**。`100%` で検索したときに、すべてのメッセージが当たらないようにするためです |
| 索引 | **`messages.body` に索引を張りません。**中間一致（`'%…%'`）では索引が効きません。20人・1チャンネル10件前後が前提なので、全表走査で足ります（仕様書 1・5-4） |
| 全文検索 | **使いません**（`FULLTEXT` ＋ ngram パーサは入れません）。日本語の語の切れ目の調整が要るうえ、上の規模では見返りがありません |
| 対象 | メッセージの本文だけ（**回答10**）。返信も含めます（Q-28 の想定）。削除済みは出しません（決定1 の出口2） |

### 決定12（仮） 操作が済んだことの知らせ

**決めたこと**: Q-34 の想定どおり出します。**セッションの flash**（`redirect()->with('status', …)`）で、移動先の画面の**本文の上に1行**だけ出します。

| 項目 | 決めたこと |
|:--|:--|
| 持ち方 | セッションの flash。**1回の遷移で消えます。**閉じるボタンは置きません |
| 置き場 | 共通レイアウトの本文の上（`screens.md` 3-1 の「操作が済んだ知らせ」の行）。**エラー画面には出しません**（決定8） |
| 見た目 | `design-guide.md` の藍系の薄地（「公開」の badge と同じ系統）。入力エラーの赤とは別物で、**知らせは成功のときだけ**です |
| 出す操作と文言 | チャンネルを作成しました／チャンネルを保存しました／チャンネルを削除しました／メンバーを追加しました／メンバーを外しました／メッセージを削除しました |
| **出さない操作** | メッセージの投稿・返信・編集。**打ったものがその場に出るので、知らせが二重になります** |
| 削除だけ出す理由 | 跡地（「このメッセージは削除されました」）は、**自分が消したのか相手が消したのかを言いません。**知らせの1行で、自分の操作が通ったことを示します（`behavior.md` 2-2 の図19 のとおり） |
| 文言の出どころ | **モックアップに見本がありません。**ボタンの「◯◯する」に対応させて「◯◯しました」の形に揃えた、型から作った文言です |
