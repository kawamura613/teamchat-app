### 決定1 削除したメッセージの本文の持ち方

**決めたこと**: メッセージの行（レコード）は残したまま、**`body` を NULL にし、`deleted_at` を立てる**。本文のデータは残しません。

#### 前提（先に論点を絞る）

どちらの案でも、**行そのものは必ず残ります**。理由は3つあり、すでに確定しています。

- 跡地に投稿者名と日時を出す（仕様書 3-4）
- 返信がぶら下がる先が要る（回答6「削除されたメッセージにも返信を続けられる」）
- 返信件数の表示を消さない（`design-guide.md` 4）

つまり「行を消すか残すか」ではなく、**`body` カラムの中身を残すか消すか**だけが論点です。どちらの案でも `deleted_at` のような印は必要で、案2は正確には「論理削除 ＋ 本文の消去」です。

#### 案1 論理削除（本文を残し、表示だけ切り替える）

| | 内容 |
|:--|:--|
| **メリット** | **間違えて消しても戻せる。**唯一にして最大の利点 |
| | Laravel の `SoftDeletes` にそのまま乗る。`deleted_at` 1本で済み、独自の書き分けが要らない |
| | グローバルスコープが既定で除外するので、公開APIと検索は「何もしなければ漏れない」。跡地を出す一覧側だけ `withTrashed()` を明示する形になり、付け忘れたときの失敗は「跡地が消える」という見た目の不具合に倒れる（漏洩に倒れない） |
| | あとから「やはり消す」へ移行できる。逆はできない |
| **デメリット** | 利用者の「消した」という理解と、実物が食い違う。誤って書いた機密や個人名がデータベースに残り続ける |
| | 漏れうる面が増え続ける。`select *` を書く人、CSVエクスポート、ログ、将来の管理画面、全文検索の仕組みを入れたときのインデックス — そのすべてで「削除済みを外す」を思い出す必要がある |
| | **残しても使う手段がない。**復元の導線は設計上どこにもない（管理者機能は仕様書 4 でスコープ外）。本文だけが溜まり、読めるのはデータベースに直接入る人だけ |
| | **編集の扱いと食い違う。**編集では古い本文を残さない設計（「編集済み」の印だけ）なので、本気で消したい人は「編集で空白に上書き」すれば痕跡なく消せる。削除だけ残すのはちぐはぐで、記録としても信用できない |

#### 案2a 物理消去（行は残し、`body` を NULL にする）── 採用

| | 内容 |
|:--|:--|
| **メリット** | 消えているので、**そもそも漏れようがない**。公開APIの口が将来増えても、エクスポートしても、雑なクエリを書いても出てこない |
| | 全文検索のインデックスが汚れない。「検索で除外し忘れる」事故が原理的に起きない |
| | 利用者の理解と実物が一致する。社内チャットでの削除の主な用途（チャンネルを間違えた・書きすぎた）に素直 |
| | 編集の扱い（古い本文を残さない）と一貫する |
| **デメリット** | **取り返しがつかない。**誤削除の救済手段がゼロになる |
| | `SoftDeletes` の既定からは少し外れ、`deleting` のタイミングで本文を落とす処理を1箇所だけ自前で書く |
| | 「あのとき何を書いたか」を確かめる手段が永久になくなる |

#### 比較

| 判断軸 | 案1 論理削除 | 案2a 物理消去 |
|:--|:--|:--|
| 誤削除から戻せるか | ◯ 戻せる | ✕ 戻せない |
| うっかり漏れる余地 | △ 常にある（除外し忘れ） | ◎ 原理的にない |
| 公開APIでの事故 | △ 実装次第（既定は安全） | ◎ 起こり得ない |
| 検索での事故 | △ 同上。全文検索を入れると要注意 | ◎ 起こり得ない |
| Laravel との相性 | ◎ `SoftDeletes` のまま | ◯ 1箇所だけ自前 |
| 編集の扱いとの一貫性 | ✕ 食い違う | ◎ 揃う |
| あとから方針を変えられるか | ◎ 消す側へ移行できる | ✕ 戻せない |
| 残したデータを使える人・画面 | **ない**（管理者機能はスコープ外） | — |

#### 案2aにした理由

1. **残しても使い道がない。**復元する画面も、記録を見る人も、この案件には存在しません（管理者機能は仕様書 4 で明確にスコープ外）。
2. **漏れうる場所が増え続ける。**公開APIという外向きの口がすでにあり、これから増える前提です。使えないデータを、漏れうる場所に置き続ける取引になっています。
3. **編集で古い本文を残さない以上、削除だけ残しても記録として信用できない。**「残っているのに使えない」が一番たちの悪い状態です。
4. **利用者の理解と実物が一致する。**「消した」と思ったものが読める状態で残っているのは、裏切りになります。

#### 承知している弱点と、その埋め方

唯一の弱点は、**誤って消したときに戻せない**ことです。これはメッセージ削除の前に確認を1枚挟むことで実用上は埋まると考え、**Q-39 として別途お聞きします**。チャンネル削除には回答2で確認が指定されているので、見せ方を揃えられます。

#### 採らなかった作り方（案2b）

`body` に「このメッセージは削除されました」という文字列を入れる形は**採りません**。

- 画面に出す**文言がデータに混ざる**。文言を変えたくなったら全行を書き換えることになる
- 利用者がその文章をそのまま打った普通のメッセージと**区別が付かない**
- 検索するとその文字列がヒットし、公開APIからも出る（回答11に反する）
- 結局 `deleted_at` も要るので、印が二重になる

状態は印（フラグ）で持ち、文言は画面側に置きます。

#### 見送った折衷案

「いったん残しておいて、N日後に本文を消すバッチを回す」という中間案もありますが、20人・社内・運用担当なしという条件では、仕組みを足すだけの見返りがないと判断しました。

#### 実装への申し送り

| 先 | 内容 |
|:--|:--|
| `data.md` | `messages.body` は nullable。空文字ではなく **NULL**（「本文がない」と「空文字を投稿した」を区別するため。そもそも空投稿は弾きます） |
| `behavior.md` | `SoftDeletes` を使い、`deleting` のタイミングで `body` を NULL にする |
| `behavior.md` | チャンネル一覧とスレッドは `withTrashed()`。検索と公開APIは既定（除外）のまま触らない |
| `behavior.md` | 返信件数は、削除済みの親・子を含めて数える（Q-23 の想定どおり） |
| `data.md` | チャンネルごと削除するときは行自体を消す（回答2）。`forceDelete` か外部キーの `onDelete('cascade')` |
