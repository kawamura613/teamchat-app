### 1-2. 読み方

| 記号 | 意味 |
|:--|:--|
| ○ | できる |
| △ | 条件つきでできる。条件は **1-4** に書いてあります |
| × | できない。**返し方（404 か 403 か）は 1-5 の決まりに従います** |
| — | この機能では、その立場であるかどうかを**判定に使いません**（画面を持たない仕組みの行では、全列が `—` です） |

- **列は「立場」で、1人が同時にいくつもの列に当たります。**たとえば自分が作ったチャンネルで自分が書いたメッセージなら、その人は C・D・E の3つに当たります。**1つでも ○ があればできます**
- `—` は「できない」ではありません。たとえば F-13（メッセージ一覧）の列D が `—` なのは、「書いた本人かどうか」を見ずに、列C（見られる人か）だけで決めるという意味です
- **△ の条件には、「ほかの列にも当たっていること」が入ることがあります。**F-15・F-16 の △3 がそれで、**列D であるだけでは足りず、いまも列C であることが絶対の前提**です（1-4）
- 判定する場所は 1-6 にまとめました

### 1-5. ×の返し方（404 と 403 の線引き）

× のときに何を返すかを、1つの決まりで統一します。

> **その人に「それがある」と知られてよいかどうかで分けます。**
> 知られてよいなら **403**（権限がありません）、知られてはいけないなら **404**（見つかりません）。

| 場面 | 返すもの | 理由 | 典拠 |
|:--|:--|:--|:--|
| 列B が、見られないプライベートチャンネルのURL（F-13・F-14・F-18・F-19 など）を開く | **404** | 403 を返すと「そこに部屋がある」ことが漏れます。「そういう部屋がある こと自体が分からない状態」にするため | 回答1 / Q-10 の想定 |
| 列B が、見られないチャンネルの中のメッセージのURL（F-15・F-16）を開く | **404** | 同上。メッセージの存在も漏らしません | 回答1 |
| 列C（作成者でない人）が F-08・F-09・F-10 のURLを開く | **403** | そのチャンネルは本人に見えているので、隠す意味がありません | 仕様書 3-2 |
| 列C（本人でない人）が F-15・F-16 のURLを開く | **403** | そのメッセージは本人に見えています（画面にも並んでいます） | 仕様書 3-4 |
| **列D だが、いまは列C でない人**（プライベートチャンネルから外された人）が、自分の過去のメッセージを編集・削除しようとする（△3 の（1）） | **404** | 先に「チャンネルを見られるか」で落ちます。403 を返すと、外されたあともそのチャンネルが残っていることが分かってしまいます | **仕様書 3-3** / 回答1 / Q-15 の想定 |
| 列D が、**削除済み**の自分のメッセージを編集・再削除しようとする（△3 の（3）） | **404** | ルートモデルバインディングの既定（削除済みを除外）でそのまま落ちます。ここだけ 403 にすると、例外をひとつ足すことになります | Q-19 の想定 / `questions.md` 決定1 |
| 列E が、**公開**チャンネルでメンバー画面（F-10〜F-12）を開く（△1） | **404** | その画面は存在しません（プライベート専用） | `members.html` |
| 列E が、**作成者の行**を外そうとする（△2） | **403** | 作成者にはそのチャンネルもメンバー画面も見えているので、隠すものがありません。画面の「外す」は押せない状態で残しますが、URLを直接叩かれたときはここで落とします（2026-11-02 に追加） | 回答4 / `members.html` |
| 列A が、ログインの要る画面を開く | **302 →** SC-01 | 「見つかりません」ではなく、ログイン画面に送ります | Q-33 の想定 |
| 列B〜E が、SC-01・SC-02 を開く（×1） | **302 →** SC-03 | ログイン済みの人にログイン画面を出す意味がないため。**できないのではなく要らない** ための × | Q-04 の想定 / Q-33 の想定 |

- **404 と 403 の分かれ目は「チャンネルを見られるか」の1点だけです。**だから判定の順番が決まります。**先に「チャンネルを見られるか」を見て、見られなければ 404。見られたうえで「作成者か／本人か」を見て、違えば 403**
- **この順番は F-15・F-16（メッセージの編集・削除）でも同じです。**「書いた本人か」を先に見ると、外されたメンバーに 403 が返って、そのチャンネルの存在が漏れます（△3 の（1））
- この順番を守るために、チャンネルの取得は**見られるものに絞った問い合わせ**で行い、見つからなければ 404 にします（ポリシーに任せると 403 になり、存在が漏れます）。詳しくは `behavior.md` 3章

### 1-6. 線引きを守る場所

| 守るもの | 置き場所 | 中身 |
|:--|:--|:--|
| 「見られるチャンネル」の絞り込み | `Channel` のスコープ（`visibleTo`） | 公開である **または** `channel_user` に自分の行がある。サイドバー（F-04）・チャンネル一覧（F-06）・検索（F-20）・チャンネルの取得が、すべてこの1つを通ります |
| チャンネルに対する可否 | `ChannelPolicy` | `view`（列C）・`update`・`delete`・`manageMembers`（列E ＋ △1） |
| メッセージに対する可否 | `MessagePolicy` | `update`・`delete`（列D ＋ △3）・`reply`（列C ＋ △4）。**どの判定も、メッセージ自体を見る前に、必ず `ChannelPolicy@view`（いまもそのチャンネルを見られるか）を先に通します。**「書いた本人か」「削除済みでないか」は、そのあとに見ます。順番を逆にすると、プライベートチャンネルから外された人が自分の過去のメッセージを直せてしまい（仕様書 3-3 に反します）、403 でそのチャンネルの存在も漏れます |
| ログイン済みかどうか | `auth` ミドルウェア | 列A を 302 で SC-01 へ |
| ログイン済みの人を入れない | `guest` ミドルウェア | ×1 の 302 |

- **サイドバー（F-04）に出すチャンネルは、View Composer（`AppServiceProvider` で `layouts.app` に合成）で渡します。**共通の枠を使う7画面すべてのコントローラーで同じ問い合わせを繰り返さないためです。渡す値は上の表の1行目と同じ `visibleTo` スコープを通したものに限ります
- **サイドバーで選択中にする行も、同じ View Composer が決めます**（`screens.md` 3-1 の「選択中の強調」）。URL の `{channel}` を見て、**無ければ `{message}` が属するチャンネル**を見ます。メッセージ1件に対するURL（`messages.edit`・`messages.show`）には `{channel}` が無いので、`{channel}` だけを見ると選択中の行が消えてしまいます。ここで「見られるか」は見ません。その判定は、画面を出す前にコントローラーと `MessagePolicy` が済ませています（1-5）（2026-11-02 に追加）

これが `features.md` の **F-05（アクセス制御）**の実体です。画面を持たないので、ほかの機能の中で一緒に動きます。

## 2. ルーティング一覧

### 2-1. 決めたこと

URLの形は仕様書・モックアップのどちらにも指定がありません（モックアップのリンクは `channel-show.html` のような静的ファイル名です）。次の決まりで引きました。

| 決まり | 内容 | 理由 |
|:--|:--|:--|
| Laravel の作法に合わせる | 複数形・ケバブケースなし・`index` / `create` / `store` / `show` / `edit` / `update` / `destroy` の名前を使う | あとから読む人が、URLとコントローラの対応を推測できる |
| 浅い入れ子（shallow nesting） | 一覧と作成は親の下（`/channels/{channel}/messages`）、1件に対する操作は親を外す（`/messages/{message}`） | Laravel が勧める形。入れ子を深くしても、メッセージIDだけで対象が決まる |
| `Route::resource` は使わない | 1本ずつ書く | SC-10（削除の確認）が `resource` の7本に無く、`show` と `edit` で通れる列が違うため、**権限マトリクスと1行ずつ突き合わせられる**ほうを採りました |
| スレッドは独立したURL | `GET /messages/{message}` | ブラウザの「戻る」で閉じられ、URLを人に送れるようにするため（Q-24 の想定） |

**ログインが要る画面には `no-store` も付けます**

表の `auth` の行は、実際には `auth` ＋ `cache.headers:no_store;no_cache;must_revalidate;max_age=0` の 2 つを通します。Laravel の既定（`no-cache, private`）では、**ログアウトしたあとにブラウザの戻るボタンで中身が履歴から出てしまい**、`acceptance.md` の AC-1-4「中身は出ずログイン画面に送られる」を満たせません（2026-11-01 に実機で確認して追加）。`login`・`register` の画面（列A が開くもの）には付けません。CSRF トークンを載せているので、既定の再検証で足ります。

**認証の5本は Fortify が登録します**

`Fortify\` は `Laravel\Fortify\Http\Controllers\` の略です。この5本（`login`・`login.store`・`logout`・`register`・`register.store`）は **`routes/web.php` には書きません**。パッケージが同じURL・同じルート名・同じミドルウェアで登録するので、上の表はそのまま読めます（4-3 の #13）。画面（SC-01・SC-02）は `Fortify::loginView()` / `Fortify::registerView()` で自前の Blade を渡します。

Fortify は **`features` と無関係に、パスワード確認の3本**（`password.confirm`・`password.confirm.store`・`password.confirmation`）も登録します。この画面は作らないので、`Fortify::confirmPasswordView()` で **404** を返します（1-5 の「作らないものは見つからない」に合わせる）。残る2本は何からも参照されず、叩いても害がないのでそのままにしています。

**ルートモデルバインディング**

`messages` は `SoftDeletes` を使うので、**既定では削除済みの行が解決されません**。ルートごとに分けます。

| ルート | バインディング | なぜ |
|:--|:--|:--|
| `messages.show`（SC-07） | **`->withTrashed()`** | 削除されたメッセージのスレッドを開ける必要があります（`thread.html` が削除済みの親で開いた状態を描いています） |
| `messages.replies.store`（F-19） | **`->withTrashed()`** | 削除されたメッセージにも返信を続けられます（回答6） |
| `messages.edit`・`messages.update`・`messages.destroy` | **既定のまま**（削除済みを除外） | 削除済みは編集・再削除ができません（△3）。バインディングで落ちるので、404 になります |
| `channels.*` | **使いません**（暗黙のバインディングを外す） | 既定のバインディングは「見られるか」を見ないので、見えないプライベートチャンネルでも解決してしまいます。そのあとポリシーで落とすと 403 になり、存在が漏れます（1-5）。コントローラーが `{channel}` を `visibleTo` に絞って引き、見つからなければ 404 にします。チャンネルは論理削除を使わないので、`withTrashed()` の出番はありません（`data.md` 3-2） |

- `{channel}` と `{user}` は `id` で引きます（スラグは持ちません・`data.md` 2-2）
- `{message}` は返信でも同じルートで受けます（返信もメッセージと同じテーブル・`data.md` 1-3 の決定1）
- **URLに出てくる `{channel}` の取得は、必ず「見られるチャンネル」に絞って行います**（1-5）
- `{channel}` は**数字だけに絞ります**（ルートの `whereNumber`）。数字でないURLはルートの時点で 404 になり、コントローラーまで来ません（`behavior.md` 3-2 の「そのURLがない」）

**検索の入力**

| 名前 | 場所 | 中身 |
|:--|:--|:--|
| `q` | クエリ文字列 | キーワード。上部バーの検索窓と SC-08 の検索欄の両方から、`GET /search?q=リリース` の形で送ります |

GET にしたのは、検索結果のURLを人に送れて、ブラウザの履歴にも残るためです（`search.html` の検索欄に入力が残っていることとも揃います）。

**返す列をリソースクラスの許可リストで持ちます。**ここに挙げたものは、列が増えても自動では出てきません（`questions.md` 決定1 の出口3）。

| 返さないもの | 理由 | 典拠 |
|:--|:--|:--|
| メールアドレス（`users.email`） | 社外から読めるところに個人のメールアドレスを出しません | Q-31 の想定 |
| ユーザーID（`users.id`） | 返す理由がありません。表示名だけで足ります | Q-31 の想定 |
| `deleted_at`・`edited_at`・`updated_at` | 削除済みは並ばないので `deleted_at` は常に `null`。編集は `edited` の真偽値で足ります | 回答11 / Q-17 の想定 |

### 3-5. エラーの返し方

**形**は1つだけです。Laravel の作法に合わせ、`message` の1本で返します。

```json
{ "message": "指定されたチャンネルは見つかりません" }
```

| 起きたこと | ステータス | `message` | 典拠 |
|:--|:--|:--|:--|
| そのIDのチャンネルがない | **404** | 指定されたチャンネルは見つかりません | — |
| プライベートチャンネルのIDを指定した | **404** | 指定されたチャンネルは見つかりません | **仕様書 3-7 / 回答1**（「ない」と「見せられない」を**同じ文言**にします。文言を分けると、プライベートチャンネルがあることが漏れます） |
| 書き込み・変更のAPIを叩いた（POST・PATCH・DELETE） | **405** | このAPIは読み取り専用です | 仕様書 3-7 |
| そのURLのAPIがない | **404** | 指定されたURLは見つかりません | — |
| 回数制限を超えた（60回／分） | **429** | リクエストが多すぎます。しばらくしてからお試しください | `RouteServiceProvider` |
| アプリ側の不具合 | **500** | サーバ側で問題が発生しました | 下記 |

- **404 の文言を揃えることが、このAPIで一番大事なところです。**「存在しません」と「プライベートなので返せません」を言い分けた瞬間に、仕様書 3-7 が破れます
- 500 では**中身を出しません**（例外のクラス名・ファイル名・SQL・本文を含めない）。`APP_DEBUG=false` が前提です
- Laravel の既定では、404 のときに `No query results for model [App\Models\Channel] 9` というモデルのクラス名入りの文が返ります。**そのままにしません**（差し替えは `behavior.md` 3章）
- 入力の検査で落ちる 422 は**起きません**。入力は `page` だけで、範囲の外なら空の `data` を返します
